# Git運用規約

## 優先順位

以下の順で優先する。

1. チーム合意、README、CONTRIBUTING、運用資料
2. リポジトリの既存運用
3. このファイル

## 基本方針

- `main` は安定版または公開中と同じ状態として扱う。
- `develop` は日常の作業を集約するブランチとして扱う。
- 通常の開発・修正・文書更新は `develop` から作業ブランチを切る。
- 緊急の本番修正だけ `main` から `hotfix/xxx` を切る。
- `main` / `develop` への直接コミットや直接 push は、チームの明示手順がある場合だけにする。
- 分からないときは操作を止めて確認する。

## ブランチ命名

既存ルールがあればそれを優先する。明示ルールがない場合のみ、次を使う。

| 用途 | パターン | 例 |
|------|---------|-----|
| 通常の開発・修正・文書更新 | `feature/<short-name>` | `feature/header-layout-fix` |
| 緊急の本番修正 | `hotfix/<short-name>` | `hotfix/login-error` |

### ルール

- 通常作業の起点は `develop`、緊急修正の起点は `main` にする。
- 説明部分は英語のケバブケースを使う。
- 2〜4語程度で短く具体的に書く。
- ブランチ作成前に、起点ブランチが最新かを確認する。
- 作業ブランチは merge 後に不要なら削除する。

## コミットメッセージ

既存ルールがなければ、prefix なしの具体的な日本語 1 行を使う。

良い例:

- `トップページのヘッダー画像を新デザインに差し替え`
- `お問い合わせフォームの送信ボタンの色を青に変更`
- `スタッフ紹介ページの誤字を修正`
- `商品詳細ページのレイアウト崩れをスマホ表示で修正`

避けたい例:

- `修正`
- `いろいろ変更`
- `fix`
- `update`
- `WIP`

### ルール

- 1コミット = 1目的
- 要約だけで「何をしたか」が分かるように書く
- 1行目は 72 文字以内を目安にする
- コミット前に `git status` と差分を確認する
- 意図しないファイルや秘密情報を混ぜない
- 作業途中の一時保存は、共有ブランチへ push する前に整理する

## Push と merge

- commit しただけでは共有されない。作業が一区切りついたら push する。
- 新しい作業ブランチの初回 push は `git push -u origin <branch>` を使う。
- `feature/xxx` の完了後は `develop` へ取り込む前に確認を行う。
- `develop -> main` はリリース手順と承認に従う。
- `force push`、`reset`、共有ブランチ削除は明示承認がある場合だけにする。
